## 一、为什么做这个项目

真实需求（用户原话整理）：

- 高老师等人通过 Telegram 提需求，Agent 能答的直接答，答不了的记进工作台，让我按顺序处理。
- 我自己也有增量任务：准备做什么、做了什么、什么没做、为什么延期、什么在等结果、到时间要去催。
- 每月底要从内部系统拉一张表，和工作台里的任务对账。
- 这是真实需求，使用场景和习惯都很明确，**不先做 MVP 验证**。

思路来源：Anthropic 2026-11-13 的《Building always-on agents》。持续运行的方向是对的，但要把"我"放进循环：**人是工作循环里的一等参与者，但不是系统持续运行的前提**。我不在的时候，系统照样推进已授权的工作，需要我判断的事进入待办；随着证据积累，逐步把我要做的事交给 Agent（Progressive Delegation）。

## 二、设计框架

### 2.1 一句话分工

WorkBench 管工作，MR-Mem 管记忆，Agent Host 管 Agent 的运行，Mind Runtime 管认知，Facetide 管人生评价，Statebar 管短期用户状态，LiteMonitor 只做桌面指示灯。详见 [SYSTEM_COMPONENT_BOUNDARIES.md](SYSTEM_COMPONENT_BOUNDARIES.md)。

### 2.2 总体结构

```
 Telegram（我 / 高老师）             LiteMonitor 任务栏（只读）
        │                                  │ GET /status/v1
        ▼                                  ▼
 ┌──────────────── Agent Host（host/pi-workbot）────────────────┐
 │ 入站暂存 → 落 WorkBench 入站 → 合并窗口 → Pi Run（工具门面）    │
 │ tool_call 守卫：问 WorkBench 能不能做 → 放行 / 申请审批 / 拒绝  │
 │ 宿主账本：事件 → 会话、结果、待发回复；重启对账与重放           │
 └───────┬───────────────────────────────┬──────────────────────┘
         │ /v1/tools/*  /v1/wake/*        │ work_memory_*（先经授权）
         ▼                                ▼
 ┌──────── WorkBench（SQLite，业务事实权威）────┐     MR-Mem（语义记忆）
 │ tasks + task_events（快照 + 不可变事件）     │
 │ 依赖 / 提醒 / 周期任务 / 承诺 / 交付物        │
 │ 委托档案与任务责任 / 审批 / Human Inbox       │
 │ wake_events（业务事件收件箱）/ outbox        │
 │ 只读看板：工作台·日历·时间线·项目池·生活      │──► Facetide summary（只读，仅 owner）
 └─────────────────────────────────────────────┘
```

### 2.3 核心设计原则（以及为什么）

1. **业务事实只有一个权威：WorkBench 的 SQL。** 模型说"已完成"不算数，只有经工具门面写入、带证据的事件才算。记忆、聊天记录、看板都不能断定任务状态。
   *原因*：多 Agent 共享同一份工作，必须有一处能回答"现在到底是什么状态"，而且要能追溯谁、凭什么改的。
2. **当前快照 + 不可变事件。** `tasks` 存现在，`task_events` 存每一次变化（before/after、原因、证据类型、来源消息）。
   *原因*：延期几次、为什么延、谁说的，都要能回看；快照让查询便宜。
3. **证据分级，强证据必须真实存在。** 结案、改官方期限、改委托需要 `explicit_user`（引用一条真实入站消息，发送人是团队成员或该任务的请求人）或 `verified_tool`（引用本任务被确认过的投递、命中的监控或已验收的交付物）。推测（`inferred`）不能当事实。
   *原因*：第三轮审计证明，只检查"有没有填来源"等于没检查，模型可以编一个 `tg://` 链接。
4. **两条互相独立的状态机。** 业务任务状态（INBOX/READY/DOING/WAITING/BLOCKED/DONE/CANCELLED）与 Host 的 Run 状态分开。Run 完成不等于任务完成。
5. **事件先落库，再交给模型。** 入站消息、到期提醒、审批结果、外部变化都先成为 WorkBench 里的持久唤醒事件，Host 再来领。
   *原因*：进程会崩、网络会断；落了库的事件才能对账、重放，不会丢。
6. **Progressive Delegation 是产品核心（ADR-0003）。** 按工作类别定委托档案（上限），任务级只能收窄；没有全局"自主分"；升级要凭验收证据，默认只提建议、等 owner 批。业务上"能不能做"由 WorkBench 判定，Host 在工具调用那一刻执行。
7. **对外动作必须可审批、只放行一次。** 审批绑定"工具 + 参数指纹 + 会话 + 任务"，批准后只在原会话放行一次。
8. **记忆由干活的 Agent 收尾时写，像交接便条。** 只记有人明确说了的、确实发生了的事，带来源；规律留给 MR-Mem 的编译层去归纳。
9. **看板只读。** 所有页面都是 GET，没有写入口；看板密码不是 Host 凭据。
10. **Pi 能力不够的地方由 Host 层补。** 账本、守卫、会话重开、合并窗口、入站暂存、回复补发都在 Host 层，不改 Pi 本身。

## 七、设计取舍

| 取舍 | 选了什么 | 没选什么 | 为什么 |
|---|---|---|---|
| 存储 | Python 标准库 + SQLite，单写事务 `BEGIN IMMEDIATE` | Postgres、ORM、消息队列 | 单人/小团队、单机；SQLite 的事务足够保证"一次 apply 全成或全不成"；依赖越少，NAS 上越好运维 |
| 任务数据 | 快照 + 不可变事件 | 纯事件溯源 / 只存快照 | 纯事件溯源查询贵、迁移难；只存快照丢历史。两者并存最实用 |
| 并发 | 乐观锁（`expected_version`），冲突就重读 | 悲观锁、自动合并 | 多 Agent 同时改同一任务时，宁可让后来者重读也不静默覆盖 |
| 委托判定位置 | WorkBench 判定、Host 执行 | 全放 Host | 委托是业务事实（哪类工作、什么上限、凭什么升级），要可审计、可复查；Host 只在工具调用那刻执行 |
| 审批粒度 | 工具 + 参数指纹 + 会话 + 任务，只放行一次 | 按工具类型整体放行 | 防止"批了一次就能发任何内容给任何人" |
| 新收件人判定 | WorkBench 查投递历史 | 模型自报 | 模型的自报不可信（第三轮审计） |
| 强证据 | 必须解析到真实记录 | 只检查字段非空 | 字段非空可以伪造 |
| 崩溃恢复 | Host 入站暂存 + WorkBench 复用原唤醒事件；回复先发再结算 | 让 Telegram 重投 / 直接重跑 | Telegram 不会重投已被处理器取走的消息；直接重跑会重复写入 |
| 记忆写入 | 干活的 Agent 收尾时写交接便条，只记说了的和做了的 | 每个事件自动进记忆 / 允许 Agent 归纳规律 | 自动全量写会把记忆变成第二个任务库；单次归纳会产生"主人常常…"这种假事实 |
| 记忆权限 | 读按聊天的人授权，写按处理的 Agent 授权 | 统一一个 token | 请求人不该读到你的工作记忆；写入是 Agent 的职责 |
| 双期限 | 日历两个标记，工作量每任务算一次 | 两个期限各算一次 / 只显示一个 | 一个任务就是一份工作；但官方 DDL 必须看得见 |
| 排期建议 | 只往前挪 Soft Due、只建议不写入 | 自动调整 / 可动官方 DDL | 官方期限是外部承诺，系统无权改；改计划要人点头 |
| 生活数据 | Facetide 只读接口 + 展示缓存，只给 owner | 跨库读 SQLite / 复制进 WorkBench | 保持 Facetide 唯一权威；人生评分是最私密的数据 |
| 看板 | 服务端渲染、零脚本、只读 | 前端框架 + 写操作 | 写操作必须经 Agent/工具门面留证据；零脚本减少攻击面 |
| LiteMonitor | 只读 JSON 插件 + 独立状态 token + 单路由监听 | 让它发 WakeSignal、管理进程、做 Agent 路由 | 插件引擎只能定时拉取和显示；定时 POST 等于无条件唤醒；唤醒事件本来就由 WorkBench 产生 |
| 统一 Host | 暂不建，`pi-workbot` 作参考实现 | 先造多 Agent 调度服务 | 只有一个消费者时造调度层是过度设计 |
| 测试 | 契约与真实失败模式；每条审计反例写成测试并在旧代码上跑一遍确认会失败 | 追求覆盖率 | 测试要证明它真能抓住问题 |
| MVP | 不做 MVP，按完整框架实现后审计补漏 | 先做最小版本验证 | 需求和使用习惯明确，MVP 只会推迟必然要做的结构 |

**需求**（用户原话整理）：多设备，希望有自己的前端页面；现在通过 Telegram 管理 session、删改记录很不方便；有些 session 的交互不想写进记忆，用完就想直接删；交互过程中产生的文件（生成的图、收到的照片）有的要留、有的用完就不要，需要集中可视化管理，否则越堆越多。

**归属判断**：session 和交互产物都是 Agent Host 的执行记录，不是 WorkBench 的业务事实。所以这是 **Host 控制台**，不放进 WorkBench 只读看板，看板保持零写入。

**做法：不自己写前端，改现成的。** 用 [agegr/pi-web](https://github.com/agegr/pi-web)（MIT），它本来就直接读 Pi 会话文件，能浏览、分叉、导出、删除会话。本地克隆在 `C:\projects\pi-web`，分支 `manage-console`，只加了下面几块，没有新增服务：

| 新增 | 做什么 |
|---|---|
| 删会话联动删记忆（`lib/memory-forget.ts`，接进 `lib/session-delete.ts`） | 删会话（含子会话）前先调 MR-Mem `/forget`，按 `session_id` 删掉引用它的记忆。**先删记忆再删文件**：MR-Mem 配了却连不上时，整个删除被拒绝，会话留着，不会出现"会话没了、记忆还在" |
| 管理模式 `PI_WEB_MANAGE_ONLY=1`（`lib/manage-only.ts`，在 `proxy.ts` 拦截） | 拒绝在网页里起 Agent、发消息、开终端、自动起标题。Agent 只走各自的网关（带网关的工具、拦截和记忆钩子），网页只做管理 |
| 交互产物画廊（`/manage` 页面 + `/api/manage/artifacts`） | 把配置的目录（溪月的 `workspace/generated`、`workspace/inbox`）里的文件集中显示，可按日期或会话分组。每个文件出自哪个会话是**推出来的**：会话原文里出现 `generated/<文件名>` 就算关联，不用改溪月生成文件的代码 |
| 保留 / 删除 / 待清理 | "保留"只是索引文件里的标记，**不移动文件**，会话和记忆里引用的路径不会失效；保留的文件不能删，要先取消保留。"待清理"列出没保留、并且没有会话再引用或超过 14 天的文件，**只列不删**，勾选后才删 |
| 删会话的预览（`/api/manage/sessions/[id]/delete-preview`） | 删之前列出：连带的子会话、会删掉的记忆（`/forget` 的 dry_run）、只有这个会话引用且没保留的文件（默认勾选，可去掉） |

工作 bot（本仓库 `host/pi-workbot`）同时补上：

- `/new`：下一条消息开新会话（以前同一个聊天一直续用 `continueRecent`，按会话删记忆会连带整段聊天历史）。
- `/incognito`：无痕会话。会话只在内存里，不落会话文件；`work_memory_write` 在工具里直接跳过；回复不写进宿主账本，入站暂存处理完立刻压缩掉原文。模式写在 `chat-modes.json`，网关重启后仍是无痕。发 `/new` 退出。
- 入站暂存 `inbound.jsonl` 启动时压缩，只留没处理完的消息（以前只追加不清理）。

**实测**（全部用合成数据，没碰溪月的真实会话和文件；第二轮换成打了补丁的真向量服务代码和同结构的检查点仓库）：

- pi-web：本地起服务，配假的 MR-Mem（同样的 `/forget` 请求和返回格式）。点"保留"、删孤立文件、删会话（预览显示 1 条记忆和 2 个只属于它的文件，去掉其中一个的勾）——结果：会话文件删了、对应记忆删了、勾上的文件删了、没勾的和保留的都还在。把假 MR-Mem 停掉再删：预览提示读不到 MR-Mem、删除被拒绝、会话还在。管理模式下 `POST /api/agent/new` 和给会话发消息都返回 403。新增测试 9 项 + 上游删除/鉴权测试，共 22 项通过；类型检查只剩上游原有的 mermaid 类型声明报错。
- 工作 bot：CLI 跑 `/new → 记一件事 → /incognito → 记一件事 → /new → 问这两件事`。无痕那条没写记忆、没有会话文件、不在入站暂存和记忆重试队列里；它建的任务照常在工作台，所以新会话能从任务里答出来。

**设计取舍**：

| 取舍 | 选了什么 | 没选什么 | 为什么 |
|---|---|---|---|
| 前端 | 改 pi-web，加一个管理页 | 自己写前端 / 塞进 WorkBench 看板 | pi-web 已有会话浏览和删除；看板要保持只读 |
| 产物来源 | 扫会话原文里的路径推出关联 | 让生成文件的代码写元数据 | 不改溪月的生成代码；路径本来就在原文里 |
| 保留 | 索引里打标记，文件原地不动 | 移进"收藏"目录 | 一移动，会话和记忆里的路径就失效 |
| 清理 | 只列候选，人勾选后删 | 定时自动删 | 只认人主动删除 |
| 删除顺序 | 先删记忆，失败就整个不删 | 先删文件、记忆失败再补 | 不留"会话没了记忆还在"的中间态，也不用补偿队列 |
| 多来源记忆 | 还有别的会话支撑就保留，只去掉被删会话这个来源 | 整条删除 | 不能矫枉过正：删一个会话不该带走别的会话也记得的事（用户 11-17 定） |
| 检查点对齐 | 删文件时改写溪月检查点历史、只删这些文件的内容对象 | 留在历史里 / 整库 `gc --prune=now` | 删了的文件不能再被 restore 回来；整库清理会和溪月自己的快照抢写入 |
| 无痕会话里的任务 | 照常进工作台 | 一并丢弃 | 任务是工作事实不是记忆；要撤销就单独取消那个任务 |

**还没做 / 要注意**：

1. **没部署**。部署到 NAS 要你授权：pi-web 需要 Node ≥ 22.19；`PI_CODING_AGENT_DIR` 指向溪月的 agent 目录时，pi-web 可能会改写那里的 `settings.json` 等文件，部署前要先确认或给它一份独立的目录副本只读会话。
2. **多来源记忆（已部署 2026-11-18）**：MR-Mem `/forget` 改成"只由这个会话支撑的记忆删除；还有别的会话支撑的保留，只去掉这个来源"。预览分两栏列出。改动是 NAS 向量服务的补丁（pi-web `deploy/mrmem-vector/`），本地用真服务代码 + 临时库测过。11-18 部署到 NAS `mrmem-vector`：原文件备份为 `service.py.bak-20261118-forget-keep-shared`，重启后 healthy，dry_run 返回带 `detached` 的新格式。回滚：把备份拷回 `service.py` 再重启容器。
3. **检查点对齐（已做）**：从画廊删文件时，同时改写溪月 `.workspace-checkpoints.git` 的历史：从第一个含这些文件的快照起逐个重建（提交信息、作者、时间不变），分支用比较交换更新（溪月同时存快照就重试），从索引去掉，再只删除这些文件、且没有别处再用到的内容对象。失败的留在待办里，下次删除时重试。之后的快照 id 会变，溪月以前给过的旧 id 无法再 restore。本地用同结构的仓库测过（`git fsck` 无损坏），NAS 上溪月现有 108 个快照，未实测。

4. 删会话后，如果溪月网关还有这个会话的记忆写入在排队，可能会在 `/forget` 之后又写回来。
5. pi-web 侧边栏原有的删除按钮也会联动删记忆，但没有预览；需要预览就从 `/manage` 删。
6. 溪月那边的无痕会话已有（`SessionManager.inMemory`），这次没动溪月网关。
