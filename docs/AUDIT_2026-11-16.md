## Confirmed findings and gates

### P0 — the task backend is not present in the remote

Remote `src/workdesk/` only contains `contracts.py`, `user_context.py` and package metadata. No concrete `TaskService` implementation, database transaction boundary, state machine, event ledger writer, optimistic concurrency enforcement, reminder leasing or inbox/outbox worker has been committed. The local earlier reference implementation has `WorkdeskStore` and related modules, but **local passing tests are not remote CI evidence**. Port and reconcile it with the new schema and actor contract, then add full, synthetic tests.

**Gate:** confirmed create/update/replay/duplicate/rollback/conflict/reminder/visibility roundtrips through the actual `WorkbenchTools` implementation.

### P0 — cross-workspace relational integrity is incomplete

In `db/schema.sql` the following references use global IDs only rather than consistent `(workspace_id, id)` constraints:

- `message_links` joins `inbox_messages(id)` and `tasks(id)` without a workspace identity; unlike `task_events`, it cannot enforce that both ends share a workspace.
- `reminders.dependency_id` references `dependencies(id)` but not the reminder's workspace/task.
- `memory_outbox.task_event_id` references `task_events(id)` but does not constrain the outbox workspace to the event workspace.
- `delivery_outbox.task_id` and `delivery_outbox.reminder_id` are similarly unscoped references.

The service must enforce access checks regardless of SQL FK strength, but schema-level composite FKs provide defense in depth. Add cross-workspace **negative insertion tests**.

**Gate:** each foreign workspace linkage fails with `PRAGMA foreign_keys=ON` in a direct SQLite test, not merely through an agent tool.

### P0 — identity and memory access must be checked at use time

`SqlMemoryGrantChecker.assert_allowed` denies ungranted/read-vs-write/revoked access when called. `MR-Mem.UserContextBinder.bind` checks `memory.read` once, but its `WorkbenchEventSourceReader.current_ref` and `render_source` reuse the previously bound context without independently confirming an intervening revocation. Ensure that contexts are strictly request-scoped and/or reauthorize every sensitive retrieval/hydration, including event-specific visibility. `memory.write` is a separate capability and must gate semantic submissions.

**Gate:** revoke grant after context creation; subsequent source hydration/read/write fails closed. Also test that a requester cannot surface the owner's private task evidence into a different MR user scope.

### P1 — original official deadline semantics are underspecified

`tasks.official_due_at`, `soft_due_at` and `planned_start_at` store UTC strings only, while `docs/SQL_MIGRATION_POLICY.md` requires original local date and IANA timezone for date-only deadlines. Add immutable original due representation (local date, zone and whether date-only) and avoid interpreting a date-only official deadline as an arbitrary midnight.

### P1 — MR-Mem pre-existing offline smoke is stale

Run `43893595210` built the Docker image, then failed in `scripts/smoke_offline.py` because `RuntimeConfig(... path_a_engine=..., placement=...)` passes removed options. The same obsolete arguments exist on MR-Mem `main`; this is **not caused by the WorkBench adapter**, but the branch's Docker quality gate is still red. The script also uses `SemanticCompiler(..., schema="tree")`, whose current constructor accepts `scene`, not `schema`. Update the smoke fixture to the current compiler contract and verify end-to-end offline behavior; do not silence the gate.

### P1 — missing release controls and integration coverage

A first-run `db/schema.sql` is not a migration history. No actual Telegram identity resolver, independent scheduler, MR-Mem outbox consumer, delivery reconciliation or read-only dashboard is deployed. CI has no domain integration suites; the repository does not yet provide a privacy/secret scan comparable to MR-Mem's existing privacy workflow.

**Gate:** migration/rollback, crash and ambiguous Telegram send, no duplicate side effects, grants after revocation, secure request identity binding, durable updates across restart and independent NAS deployment must pass before production release.

## Recommended implementation order

1. Stabilize MR-Mem #22: lint fix already committed; repair outdated smoke fixture separately and rerun both workflow gates.
2. Port `WorkdeskStore` / identity / scheduler / intake / memory modules from the existing local reference into separate WorkBench modules. Avoid blindly copying the older schema over the current user-grant tables.
3. Fix cross-workspace FK invariants, date provenance and migration story; add failure-mode and integration tests.
4. Wire verified principal/role through SQL TaskService; require task version for state-changing operations and fail stale writes.
5. Wire Telegram intake and durable outgoing messages; use dry-run for live destinations until manually authorized.
6. Connect MR-Mem via scoped SourceRef + a host-owned outbox and validate source lifecycle, including revocation.
7. Add dashboard, container deployment, backup/restore drill and acceptance sign-off.

## Release decision

**Do not merge either draft PR as a finished backend, and do not deploy.** Keep draft branches; the existing code establishes module boundaries and grants but not the task lifecycle service. No customer messages, private memory data, credentials or live integrations were used in this audit.
